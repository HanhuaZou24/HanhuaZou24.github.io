Case study

Two pieces of work from CSI205TC Networking and Distributed Computing: a video streaming system implemented on both a reliable stream and an unreliable datagram transport, and the measurement of the site you are reading right now.

1. Video streaming over TCP and UDP

The brief was to build a Python video streaming application twice — once on TCP and once on UDP — and to compare them with a packet capture. Both versions carry the same 640×480 JPEG frames from a server process to a client process; the only variable is the transport underneath.

Design

  • TCP: each frame is one length-prefixed message, so the receiver can always re-synchronise on a message boundary. TCP supplies retransmission and ordering; the application only has to frame.
  • UDP: each frame is split into 1300-byte chunks carrying a 20-byte header with a frame id, a chunk index and a count. The receiver reassembles by header, not by arrival order, and drops a frame that is missing any chunk.
  • Measurement: the sender writes a monotonic timestamp into every header, so the receiver reports one-way latency and interarrival jitter for every single frame rather than one bulk transfer time.

Measured result

Four scenarios, 600 frames each: two on a clean loopback path, two with an emulated impairment. The impairment was applied by a relay process on the wire, so the dropped datagrams really never arrive and the capture shows the gap.

What the capture shows

The interesting number is not the 27.5 %: it is why 2 % of datagrams became 27.5 % of frames. A frame survives only if every one of its fragments survives, so the frame delivery ratio is (1 − p)n with n ≈ 17 fragments per frame. The model predicts 29.2 % loss; the client measured 27.5 %.

In the capture of the impaired run, frame 5 received 15 of its 16 fragments — chunk 11 never arrived — and the arrival order was 3, 7, 12, 8, 14, 5, 4, 9, 1, 13, 10, 6, 2, 16, 15. Nothing in the protocol notices either the loss or the reordering: there is no acknowledgement to time out and no retransmission to trigger. That absence is exactly the trade UDP makes, and it is why real live video layers RTP, NACK and FEC on top rather than sending bare datagrams.

Reducing n is the most effective lever: an encoder producing 4 kB frames would need three fragments, and 2 % loss would cost about 6 % of frames instead of 28 %.

Full detail — including the per-frame latency distributions, the packet-size histogram and the tshark analysis of both captures — is in the Question 1 report.

2. Measuring this website

This page is served by GitHub Pages over HTTPS. That makes it a convenient target for a layered measurement: the same visit exercises DNS, TCP, TLS and HTTP, and each layer can be timed and captured separately.

The protocol stack of one visit

LayerProtocolWhat it does for this page
ApplicationHTTP/2 over TLS 1.3 requests the HTML, CSS and JavaScript; multiplexes them on one connection
PresentationTLS 1.3 encrypts the exchange and validates the certificate for the domain
TransportTCP ordered, reliable delivery; connection established with a three-way handshake
NetworkIP routes packets between the client and GitHub’s CDN addresses
NamingDNS resolves the host name to four GitHub Pages addresses

How it is measured

  • DNS — nslookup for the name, plus the resolution time measured by the resolver call itself.
  • Reachability and latency — ping for round-trip time and tracert for the path, run from the client machine.
  • Connection setup — TCP connect time and TLS handshake time, measured separately so the cost of each layer is visible.
  • Packet level — a Wireshark capture of the DNS query, the TCP handshake, the TLS ClientHello/ServerHello and the HTTP response, filtered to this domain only.

The measurement script and the capture are part of the same coursework package as this site, and the numbers are reported alongside the capture evidence in the Question 2 section of the report.
